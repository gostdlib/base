# sets

`sets` works like [stringer](../stringer): point it at a type declared in your
package and it generates a source file for that package. For a type `T` it
declares a package-level **value**

```go
var TSet = immutable.NewSet([]T{ /* ... */ })
```

where `immutable.Set` is
[`github.com/gostdlib/base/values/immutable`](https://pkg.go.dev/github.com/gostdlib/base/values/immutable)'s
immutable set. By default the set holds the package's constants of type `T`;
with `-v` it holds values given on the command line instead.

## Install

The tool is registered in this module's `go.mod` `tool` block, so it runs via:

```bash
go tool github.com/gostdlib/base/values/generators/sets -t T
```

In another module, add it as a tool dependency first:

```bash
go get -tool github.com/gostdlib/base/values/generators/sets
```

## Usage

Add a `//go:generate` directive in the package that declares the type, then run
`go generate ./...`:

```go
//go:generate go tool github.com/gostdlib/base/values/generators/sets -t Color

type Color string

const (
	Blue Color = "blue"
	Red  Color = "yellow"
)
```

The tool type-checks the package. Each named type must be declared there and its
underlying type must be a `string`, `int`/`int8`/`int16`/`int32`/`int64`,
`uint`/`uint8`/`uint16`/`uint32`/`uint64`, or `float32`/`float64`. Without `-v`,
the type must have at least one constant declared in the package. Constants must
be declared *with* the type — an untyped `const Foo = "bar"` is not collected —
and unexported types and constants work like exported ones. With no arguments the
tool processes the package in the current directory; otherwise the one argument
must name a directory holding a Go package.

The package does not need to compile. Code referencing the not-yet-generated
`<Type>Set` is expected the first time `go generate` runs, so type errors are
tolerated; they are reported only if they prevent a named type from resolving.

### Flags

| Flag | Description |
|------|-------------|
| `-t` | **(required)** Comma-separated list of type names to generate sets for. |
| `-v` | Comma-separated values to put in the set instead of the package's constants. Requires exactly one type; each value is validated against the type's underlying type. |
| `-output` | Output file name. Defaults to `<type>_set.go`, lower-cased from the first type listed. |

## Generated code

The directive above produces `color_set.go`:

```go
// Code generated by "sets -t Color"; DO NOT EDIT.

package paint

import "github.com/gostdlib/base/values/immutable"

// ColorSet is an immutable set holding the constant values of type Color.
var ColorSet = immutable.NewSet([]Color{Blue, Red})
```

With explicit values instead:

```bash
sets -t Color -v teal,mauve
```

```go
// ColorSet is an immutable set of Color values.
var ColorSet = immutable.NewSet([]Color{"teal", "mauve"})
```

Either way the var is used directly:

```go
ColorSet.Contains(Blue)
warm := ColorSet.Intersection(immutable.NewSet([]Color{Red}))
```

Both modes name the var `<Type>Set`, so generate at most one set per type in a
package.
